If your app already uses wagmi, create the ensforge client from the wagmi config. Reads go through wagmi's client, and writes use whichever wallet is connected when they run. It works the same with RainbowKit, ConnectKit, Dynamic, Privy and Reown AppKit, because they all sit on a wagmi config.

## Prerequisites

- A wagmi 2 or 3 config, with a transport for the ENS chain.
- [`@ensforge/react` installed](/docs/react/installation).

## Create the client and render the provider

`Ensforge.fromWagmi(config)` lives on the `Ensforge` from `@ensforge/sdk/wagmi`, so apps without wagmi never load it. Render `EnsforgeProvider` inside the wagmi providers.

**Example** (Ensforge Inside The Wagmi Providers)

```tsx no-check title="providers.tsx"
import type { ReactNode } from "react";

import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { createConfig, http, WagmiProvider } from "wagmi";
import { mainnet } from "wagmi/chains";

import { EnsforgeProvider } from "@ensforge/react";
import { Ensforge } from "@ensforge/sdk/wagmi";

const wagmiConfig = createConfig({
  chains: [mainnet],
  transports: { [mainnet.id]: http() },
});
const queryClient = new QueryClient();
const ens = Ensforge.fromWagmi(wagmiConfig);

export function Providers({ children }: { children: ReactNode }) {
  return (
    <WagmiProvider config={wagmiConfig}>
      <QueryClientProvider client={queryClient}>
        <EnsforgeProvider client={ens}>{children}</EnsforgeProvider>
      </QueryClientProvider>
    </WagmiProvider>
  );
}
```

With RainbowKit or another wallet kit, put its provider around `EnsforgeProvider` in the same place.

## What `fromWagmi` does for you

- The ENS chain is the `chainId` option, else mainnet when the config has it, else the first configured chain ensforge has a deployment for. Its transport must be in the wagmi config. Otherwise it throws [`UNKNOWN_CHAIN`](/docs/reference/errors/UNKNOWN_CHAIN).
- The wallet is looked up on every write, so account and connector changes are followed. With no wallet connected, a write fails with [`WALLET_NOT_CONFIGURED`](/docs/reference/errors/WALLET_NOT_CONFIGURED).
- A wallet on another chain is asked to switch first, as wagmi's own `writeContract` does. Pass `switchChain: false` to turn that off. A wallet on another chain then fails with [`CHAIN_MISMATCH`](/docs/reference/errors/CHAIN_MISMATCH).
- Every other chain of the wagmi config becomes one of the client's `chains`, so writes ENS makes there (an L2 [primary name](/docs/reference/glossary#primary-name)) use wagmi's clients and wallet.

## Add the chains where names live

Some names live on an L2, not on Ethereum: Basenames on Base, Linea Names on Linea, and others. ensforge reads them on their L2. It uses wagmi's transport when the config has the chain, and the chain's public RPC when it does not. A write on such a name is signed on its L2, so the wallet must switch there. wagmi switches only to chains in its config.

| Chain        | ID     | Needed to write                                                  |
| ------------ | ------ | ---------------------------------------------------------------- |
| Base         | 8453   | Basenames, Durin and Namespace names on Base, Base primary names |
| OP Mainnet   | 10     | Namespace names on OP Mainnet, OP Mainnet primary names          |
| Linea        | 59144  | Linea Names, Linea primary names                                 |
| Celo         | 42220  | Celonames                                                        |
| Arbitrum One | 42161  | Arbitrum primary names                                           |
| Scroll       | 534352 | Scroll primary names                                             |

Add the chains your users write on, each with a transport. A write on a chain the config does not have fails with [`CHAIN_NOT_CONFIGURED`](/docs/reference/errors/CHAIN_NOT_CONFIGURED) before the wallet is asked.

**Example** (A Config With Base)

```tsx no-check title="wagmi.ts"
import { createConfig, http } from "wagmi";
import { base, mainnet } from "wagmi/chains";

export const wagmiConfig = createConfig({
  chains: [mainnet, base],
  transports: { [mainnet.id]: http(), [base.id]: http() },
});
```

Mainnet stays the ENS chain, because the config has it. Base becomes one of the client's chains, so reads and writes of Basenames go through wagmi.

**Example** (A Sepolia Client Without Chain Switching)

```ts no-check title="ens.ts"
import { Ensforge } from "@ensforge/sdk/wagmi";

import { wagmiConfig } from "./wagmi";

export const ens = Ensforge.fromWagmi(wagmiConfig, { chainId: 11155111, switchChain: false });
```

## Troubleshooting

### A write fails with `WALLET_NOT_CONFIGURED`

No wallet is connected. Connect one first, then send the write.

### A write fails with `CHAIN_NOT_CONFIGURED`

The name lives on an L2 the wagmi config does not have. Add that chain and its transport to the config. The error's `context.chainId` names the chain.

### `fromWagmi` throws `UNKNOWN_CHAIN`

The wagmi config has no chain ensforge can use, or no transport for it. Add mainnet, or another chain ensforge has a deployment for, with a transport. For any other chain, pass `chainId` with a `deployment`.

See [Create a client](/docs/sdk/create-a-client) for every client option, and [Set up the provider](/docs/react/set-up-the-provider) for the provider's props.
