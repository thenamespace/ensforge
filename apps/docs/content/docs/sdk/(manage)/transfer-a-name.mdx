You will send a [name](/docs/reference/glossary#name) you own to another address. ensforge moves the right token for the name's kind, so one call works for [ENSv2](/docs/reference/glossary#ensv2) names, unwrapped [ENSv1](/docs/reference/glossary#ensv1) names and wrapped names.

## Prerequisites

- A wallet client for the account that owns the name. See [Create a client](/docs/sdk/create-a-client).
- A registered name. Expired, reserved and unregistered names cannot be transferred.

## 1. Send the name

[`name.transfer`](/docs/reference/sdk/name/transfer) takes the name and the recipient. `name.transferSync` also waits for the receipt.

**Example** (Sending a Name)

```ts title="transfer.ts"
import { createWalletClient, http, type Hex } from "viem";
import { privateKeyToAccount } from "viem/accounts";
import { sepolia } from "viem/chains";
import { Ensforge, ensActions } from "@ensforge/sdk";

const account = privateKeyToAccount(process.env.PRIVATE_KEY as Hex);
const transport = http(process.env.SEPOLIA_RPC_URL);

const ens = Ensforge.create({
  chain: sepolia,
  transports: { [sepolia.id]: transport },
  wallet: createWalletClient({ account, chain: sepolia, transport }),
}).extend(ensActions());

const { hash } = await ens.name.transfer({
  name: "ensforge-docs-demo.eth",
  to: "0xB0b0000000000000000000000000000000000000",
});
```

What moves depends on where the name lives:

| Name                           | What `transfer` moves                                         |
| ------------------------------ | ------------------------------------------------------------- |
| On ENSv2                       | The name's registry token.                                    |
| Wrapped on ENSv1               | The NameWrapper token.                                        |
| Unwrapped `.eth` name on ENSv1 | The registrar token and the registry ownership (the manager). |
| Other unwrapped ENSv1 name     | The registry owner.                                           |

| Option          | Type                      | Default   | Description                                                                                   |
| --------------- | ------------------------- | --------- | --------------------------------------------------------------------------------------------- |
| `name`          | `string`                  | required  | The name to send. Normalised automatically.                                                   |
| `to`            | `string`                  | required  | The recipient address.                                                                        |
| `role`          | `"owner" \| "registrant"` | `"owner"` | Unwrapped `.eth` names only. `"registrant"` moves only the registrar token.                   |
| `unsafe`        | `boolean \| "auto"`       | `"auto"`  | ENSv2 only. How the token moves. See [Safe and unsafe transfers](#safe-and-unsafe-transfers). |
| `delegates`     | `"keep" \| "revoke"`      | `"keep"`  | ENSv2 only. What happens to roles other accounts hold on the name.                            |
| `records`       | `"keep" \| "handover"`    | `"keep"`  | ENSv2 only. What happens to the sender's roles on the name's resolver.                        |
| `setEthAddress` | `boolean`                 | `false`   | Point the name's ETH address at the recipient first, in the same step.                        |

## Safe and unsafe transfers

An ENSv2 registry allows a safe transfer only when it is emancipated and the owner alone holds the name's unemancipated roles. Otherwise someone else keeps some control of the name after it moves: the registry's root role holders, or the accounts holding those roles.

With the default `unsafe: "auto"`, ensforge sends a safe transfer when the registry allows one. Otherwise it sends `unsafeTransfer`, which still checks that the recipient can receive the name, and the plan carries a `TRANSFER_UNSAFE` warning saying why. `unsafe: true` always sends `unsafeTransfer`. `unsafe: false` fails before sending instead: with `REGISTRY_NOT_EMANCIPATED`, or with `TRANSFER_DISALLOWED` when other accounts hold roles.

Subnames created with `subname.create` sit in registries that are not emancipated by default, so their transfers are unsafe.

## Revoke other accounts' roles

Roles other accounts hold on an ENSv2 name stay with them after the transfer, and the plan carries a `ROLES_RETAINED` warning naming them. Pass `delegates: "revoke"` to revoke them in the same step, before the move. The indexer lists the accounts that hold roles, and ensforge checks each one on chain. The transfer is refused with `INDEXER_BEHIND` when they do not account for every role, so no holder is left behind silently. Without an indexer it fails with `INDEXER_NOT_CONFIGURED`.

Roles the sender has no admin role for cannot be revoked; they stay, with the warning.

## 2. Decide who keeps control of the records

On ENSv2, a name's [resolver](/docs/reference/glossary#resolver) has its own [roles](/docs/reference/glossary#role). By default they stay with the sender, who can still edit the records after the transfer. The plan carries a `RECORD_CONTROL_RETAINED` warning.

Pass `records: "handover"` to grant them to the recipient and revoke the sender's in the same step.

**Example** (Handing Over Record Control)

```ts title="transfer-handover.ts"
import { createWalletClient, http, type Hex } from "viem";
import { privateKeyToAccount } from "viem/accounts";
import { sepolia } from "viem/chains";
import { Ensforge, ensActions } from "@ensforge/sdk";

const account = privateKeyToAccount(process.env.PRIVATE_KEY as Hex);
const transport = http(process.env.SEPOLIA_RPC_URL);

const ens = Ensforge.create({
  chain: sepolia,
  transports: { [sepolia.id]: transport },
  wallet: createWalletClient({ account, chain: sepolia, transport }),
}).extend(ensActions());

await ens.name.transferSync({
  name: "ensforge-docs-demo.eth",
  to: "0xB0b0000000000000000000000000000000000000",
  records: "handover",
});
```

`"handover"` is refused for the sender's shared `"owned"` resolver, because its roles cover other names too. See [Resolvers and shared records](/docs/sdk/resolvers-and-shared-records).

## Give a subname away as its parent's owner (ENSv1)

`name.transfer` sends a name as its holder. To give an ENSv1 subname to another account as the owner of its parent, use [`subname.update`](/docs/reference/sdk/subname/update) with `owner`. See [Create subnames](/docs/sdk/create-subnames).

## Give only the registrar token (ENSv1)

An unwrapped `.eth` name on ENSv1 has two holders. The [registrant](/docs/reference/glossary#registrant) holds the registrar token and owns the name. The [manager](/docs/reference/glossary#manager) is the registry owner and edits records and subnames. See [Who can change a name](/docs/sdk/who-can-change-a-name).

- `role: "registrant"` on `name.transfer` moves only the registrar token.
- [`name.setManager`](/docs/reference/sdk/name/set-manager) lets another account edit records and subnames while you keep ownership.
- [`name.reclaim`](/docs/reference/sdk/name/reclaim) resets the manager to the registrant (or to `owner`). Use it after receiving a registrar token, or to repair a lost manager.

`setManager` and `reclaim` fail with [`UNSUPPORTED_PROTOCOL`](/docs/reference/errors/UNSUPPORTED_PROTOCOL) for ENSv2 names and wrapped names, and `reclaim` also for names that are not `.eth` names. ENSv2 uses roles instead. See [Roles and permissions](/docs/sdk/roles-and-permissions).

## Names on L2s

For a name that lives on an L2, `name.transfer` moves its token on the L2: an ERC-721 token, or Linea Names' NameWrapper token. A Basenames second-level name also moves its registry record unless `role` is `"registrant"`. `records: "handover"` is not needed there: the records follow the owner. See [Work with names on L2s](/docs/sdk/names-on-l2s).

## Check the result

Read the name with [`name.get`](/docs/reference/sdk/name/get) and compare `owner` with the recipient. See [Get a name's owner, expiry and status](/docs/sdk/get-name-details).

## Troubleshooting

### `NOT_OWNER`

The signer does not own the name. Send from the owner's account. See [`NOT_OWNER`](/docs/reference/errors/NOT_OWNER).

### `TRANSFER_DISALLOWED`

The owner lacks the role to transfer, other accounts hold roles on an ENSv2 name and `unsafe` is `false`, or the recipient (an HCA) refuses it. Revoke the other roles with `delegates: "revoke"`, or keep the default `unsafe: "auto"`. See [`TRANSFER_DISALLOWED`](/docs/reference/errors/TRANSFER_DISALLOWED).

### `INDEXER_BEHIND`

With `delegates: "revoke"`, the indexer did not list every account that holds roles on the name. Retry once it catches up, or keep the roles with `delegates: "keep"`. See [`INDEXER_BEHIND`](/docs/reference/errors/INDEXER_BEHIND).

### `NAME_EXPIRED`, `NAME_RESERVED` or `NAME_NOT_REGISTERED`

Only registered names can be sent. See [`NAME_EXPIRED`](/docs/reference/errors/NAME_EXPIRED), [`NAME_RESERVED`](/docs/reference/errors/NAME_RESERVED) and [`NAME_NOT_REGISTERED`](/docs/reference/errors/NAME_NOT_REGISTERED).

### `UNSUPPORTED_PROTOCOL`

You passed `role: "registrant"` for a name that has no registrant. See [`UNSUPPORTED_PROTOCOL`](/docs/reference/errors/UNSUPPORTED_PROTOCOL).

### `INVALID_ADDRESS`

`to` is not an address. See [`INVALID_ADDRESS`](/docs/reference/errors/INVALID_ADDRESS).
