**Write** · Stable · Since 1.0.0

Sends any plan: one prepared by a write's `.prepare`, or several combined with `Plan.merge`. Resolves once the transaction is submitted.

## When to use

Use to review a plan before sending it, or to send several writes as one flow. Use [`sendSync`](/docs/sdk/reference/actions/plan/send#wait-for-the-receipt-with-sendsync) to wait for the receipt.

## Returns

Resolves to `Write.Result`. Submitted transaction hashes and the plan that produced them.

| Field | Type | Description |
| --- | --- | --- |
| `hash` | `Hex` | Hash of the last transaction. |
| `hashes` | `readonly Hex[]` | Every submitted transaction, in order. |
| `id` | `string` | EIP-5792 bundle id when the calls were sent as one batch. |
| `plan` | `Plan` | The plan the write executed: its steps, in order, as they were submitted. |

## Wait for the receipt with `sendSync`

Sends any plan: one prepared by a write's `.prepare`, or several combined with `Plan.merge`. Resolves once the receipt is in.

Use when the next step depends on the change being on-chain.

`plan.sendSync` takes the same options plus [`confirmations` and `timeout`](/docs/sdk/reference/client#sync-options).

Resolves to `Write.SyncResult`. Receipts plus the submitted hashes and plan.

## Details

- The plan is simulated, then sent step by step; consecutive steps share one wallet bundle
  when the wallet supports atomic batches (`maxBundleCalls`), never across a chain-time wait.
- Progress is saved to the client's `storage`, so a failed or interrupted plan continues
  with [`plan.resume`](/docs/sdk/reference/actions/plan/resume); failures carry `context.planId`.
- `onStep` reports each step as it waits, is submitted, confirmed or fails.
- A plan for one of the client's `chains` (an L2 primary name) is simulated and sent there.
