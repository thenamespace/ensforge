## Capabilities

Deployments differ in some behaviours; ensforge reads these flags instead of the chain ID.

| Capability | mainnet | sepolia | Description |
| --- | --- | --- | --- |
| `resolutionErrorWrapping` | `true` | `false` | Resolution contracts wrap registry reverts in `ResolutionError(address,bytes)` and reject foreign `OffchainLookup` senders with `InvalidOffchainLookup()`. |
| `wrapperRegistryInitializer` | `fuse-derived` | `explicit` | How WrapperRegistry `initialize` receives its label and roles: passed `explicit`ly (`initialize(bytes32,address,string,uint256)`) or `fuse-derived` from NameWrapper fuses (`initialize(bytes32,address)`). |
| `wrapperRegistryEmancipation` | `role-derived` | `static` | How WrapperRegistry `isEmancipated` is computed: `static` (always `true`) or `role-derived` (from the unemancipated role bitmap). |
| `lockedMigrationRenewal` | `max-expiry` | `renew-role` | How locked migration treats names with `CAN_EXTEND_EXPIRY`: grant the `renew-role`, or set the expiry to `max-expiry` (`type(uint64).max`). |
| `userRegistryUpgradeGate` | `true` | `true` | User registries only upgrade to implementations approved by `UPGRADE_SET()`. |
| `userRegistryRootRenewal` | `true` | `false` | Registries running `implementations.userRegistry` check the `renew` role at their root only (contracts-v2 #505, mainnet since 2026-11-17). Every other registry, including those created on an earlier UserRegistry implementation, also accepts it on the name. |
| `hcaSameChainSourceRejected` | `true` | `false` | The HCA validator rejects permits whose source chain is the current chain. |
| `hcaSessionDomain` | `smart-session` | `smart-session` | EIP-712 domain HCA session approvals are signed under: Rhinestone's `smart-session` domain (contracts-v2 v1.0.1), or a dedicated `hca` domain (contracts-v2 #498, not deployed). |
| `hcaContractOwners` | `false` | `false` | HCA owners can be contracts that sign with ERC-1271 (contracts-v2 #499, not deployed). |

### `Deployments.define`

Validates a custom profile (a devnet, a fork or a chain ensforge does not ship) and returns it
unchanged.

```ts
function define<const profile extends Profile>(profile: profile): profile
```

Checks that the chain IDs agree, that every required contract group and address is present and
well-formed, and that every capability flag has a known value. It does not read the chain.

```ts title="Defining a devnet profile"
import { Deployments } from "@ensforge/contracts"

const devnet = Deployments.define({
  name: "devnet",
  chainId: 31337,
  v2: { ...devnetAddresses, capabilities: Deployments.mainnet.v2.capabilities },
})
```

Errors:

- `` `Deployments.InvalidProfileError` listing every problem found.

### `Deployments.namespaceOf`

Returns the L2 namespace whose ENS resolver is `resolver`, or `undefined` when no listed
namespace uses it.

```ts
function namespaceOf(options: { readonly chainId: number; readonly resolver: string; }): { readonly id: NamespaceId; readonly network: NamespaceNetwork } | undefined
```

`resolver` is the resolver of the parent name on the ENS chain `chainId`. Matching the resolver,
not the name, also finds every Durin and Namespace parent.

```ts title="Finding the namespace of a parent name"
import { Deployments } from "@ensforge/contracts"

Deployments.namespaceOf({
  chainId: 1,
  resolver: "0xde9049636F4a1dfE0a64d1bFe3155C0A14C54F31",
})
// { id: "basenames", network: "mainnet" }
```

import { Deployments } from "@ensforge/contracts"

const { chainId, contracts } = Deployments.namespaces.basenames.mainnet
