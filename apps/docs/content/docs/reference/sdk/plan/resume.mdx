Continues a saved plan after a failure or a reload. Resolves once the remaining transactions
are submitted.

## When to use

Use when a registration, migration or other multi-step write stopped part-way. Use
[`resumeSync`](/docs/reference/sdk/plan/resume#wait-for-the-receipt-with-resumesync) to wait for the receipts.

## Details

- Steps submitted before are confirmed, not sent again; a dropped transaction or a failed
  bundle is sent again.
- Each remaining step is simulated against current state right before it is sent.
- The plan id is `result.plan.id`, or `context.planId` on a write's error.
- A plan for another chain (an L2 primary name) resumes on that chain's clients from the
  client's `chains`.

<Callout type="warn" title="Gotchas">

- Plans live in the client's `storage`: pass `Plan.localStorage()` to survive page reloads.

</Callout>

## Returns

Resolves to `Write.Result`. Submitted transaction hashes (earlier steps included) and the plan.

| Field | Type | Description |
| --- | --- | --- |
| `hash` | `Hex` | Hash of the last transaction. |
| `hashes` | `readonly Hex[]` | Every submitted transaction, in order. |
| `id` | `string` | EIP-5792 bundle id when the calls were sent as one batch. |
| `plan` | `Plan` | The plan the write executed: its steps, in order, as they were submitted. |

## Wait for the receipt with `resumeSync`

Continues a saved plan and resolves once every receipt is in.

Use when the next step depends on the plan being finished on-chain.

`plan.resumeSync` takes the same options plus [`confirmations` and `timeout`](/docs/reference/sdk/client#sync-options).

Resolves to `Write.SyncResult`. Receipts plus the submitted hashes and plan.
